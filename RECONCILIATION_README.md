# Фикс: зависшие в "Ожидание" платежи Platega

## Причина

В коде уже было ЗАЛОЖЕНО, что должна существовать фоновая сверка —
докстринг `app.webhooks.platega.process_status_update` прямо ссылается
на несуществующий модуль:

> "...для фоновой сверки (`app.services.platega_reconciliation`,
> вызывается по опросу API, когда колбэк не дошёл — например, из-за
> смены адреса туннеля)"

Но самого модуля `app.services.platega_reconciliation` в репозитории
не было — только этот комментарий и метод `get_transaction_status()` в
`app.services.platega`, которым сверка должна была бы пользоваться.
Из-за этого: если колбэк от Platega по какой-то причине не доходит до
вашего вебхука — платёж навсегда остаётся в PENDING ("Ожидание"),
потому что его статус больше никто и никогда не переспрашивает.

## Вероятная причина, почему колбэк не доходит именно у вас

Судя по скриншоту настроек Platega из нашего разговора раньше, ваш
Callback URL — `https://mental-enjoying-forum-blanket.trycloudflare.com/webhooks/platega`.
Это **Cloudflare Quick Tunnel** — у таких адресов домен НЕ статичный,
он выдаётся заново при каждом перезапуске процесса `cloudflared`
(перезагрузка VM, падение процесса, обновление и т.п.). Если адрес
сменился, а в личном кабинете Platega старый Callback URL никто не
обновил руками — все колбэки с этого момента улетают в никуда, без
единой видимой ошибки ни у вас, ни у Platega. Платежи после этого
момента будут зависать в PENDING один за другим, а не по одному
случайно — это стоит проверить в первую очередь: откройте настройки
Platega и сверьте текущий Callback URL с реальным адресом вашего
туннеля прямо сейчас.

Если хотите зависимость от переменчивого Quick Tunnel убрать
насовсем — переезд на постоянный домен (либо platform вроде Cloudflare
Named Tunnel с закреплённым поддоменом, либо обычный домен + reverse
proxy) закрывает проблему в корне. Это отдельная задача, могу помочь
отдельно, если понадобится.

## Что делает этот патч

`app/services/platega_reconciliation.py` — сама сверка:
- раз в 5 минут проверяет все `PlategaPayment` в статусе PENDING,
  которым больше 10 минут (совсем свежие не трогает — пользователь мог
  ещё не успеть заплатить) и не больше 2 суток (совсем древние —
  закрывать нужно вручную из админки, не пытаться опрашивать API
  бесконечно);
- для каждого спрашивает у Platega актуальный статус
  (`get_transaction_status`) и, если он финальный
  (CONFIRMED/CANCELED/CHARGEBACKED), проводит его через тот же
  `process_status_update`, что и обычный вебхук — то есть выдача
  подписки/уведомление пользователя/реферальный бонус происходят
  ровно так же, как если бы колбэк дошёл вовремя;
- идемпотентна и безопасна к одновременному срабатыванию с вебхуком
  (см. докстринг `process_status_update` — платёж, уже переведённый в
  терминальный статус, повторно не обрабатывается).

`app/api.py` — запускает эту сверку как фоновую задачу при старте
`vpnapi.service`, рядом с уже существующим `init_models()`.

## Что делать с уже зависшим платежом прямо сейчас

Не обязательно ждать деплоя и первого цикла сверки — можно запустить
разовый прогон вручную прямо на сервере:

```bash
cd /opt/vpn-bot
.venv/bin/python -m app.services.platega_reconciliation
```

Выведет, сколько платежей удалось сдвинуть с PENDING. После накатки
патча это же само будет происходить каждые 5 минут в фоне, без вашего
участия.

## Как накатить

```bash
scp app/services/platega_reconciliation.py user@your-vm:/opt/vpn-bot/app/services/platega_reconciliation.py
scp app/api.py user@your-vm:/opt/vpn-bot/app/api.py

sudo systemctl restart vpnapi.service
sudo systemctl status vpnapi.service --no-pager
journalctl -u vpnapi.service -n 30 --no-pager
```

Только `vpnapi.service` — бот эта сверка не касается, `process_status_update`
уже сам поднимает свой собственный `Bot()` для уведомлений (см.
комментарий в `app/webhooks/platega.py`), как и для обычного вебхука.
